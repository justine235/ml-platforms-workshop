# Fabric end to end: ETL, ML and MLOps

This folder is the Fabric half of Part 3 (slides P3.0 to P3.14). It holds two kits that run one after the other on the same lakehouse, `lh_fleet`. The data is synthetic ("Contoso Fleet"): telematics logs, maintenance work orders and an asset register, generated by `..\02-demo-data`.

## Map

| Segment | Folder | What it builds | Live: short / full path |
|---|---|---|---|
| Demo 2a, ETL | `etl\` | Notebooks `nb_00_setup` to `nb_03_gold_reconcile` and pipeline `pl_fleet_etl`. Raw files become bronze, silver and gold tables. The gold step reconciles telematics fault episodes with work orders. | 15 / 25 min |
| Demo 2a, ML and MLOps | `ml-mlops\` | Notebooks `nb_04_features` to `nb_08_promotion_gate`, pipeline `pl_fleet_daily`, Variable Library `fleet_mlops` and `cicd\`. Features, MLflow training and tracking, a registered model, batch scores, a drift report and a promotion gate. | 18 / 30 min |
| Checker | `tools\check_fabric_git.py` | Static check of the Fabric Git folders of both kits. | seconds |

Every kit has the same files: `README.md` (what and why), `rebuild-guide.md` (rebuild from an empty tenant), `run-of-show.md` (minute by minute), `troubleshooting.md`, `VERIFY-BEFORE-FRIDAY.md` (what to re-check in a real tenant), and a `*-facts-for-slides.md` file with the numbers and code quoted on the slides.

## How the minutes are used

The deck gives the Fabric half 55 minutes: framing 11, ETL 17, ML and MLOps 27. The live demo inside those minutes uses the short paths, about 15 + 18 = 33 minutes. The full paths (25 + 30 minutes) are for a longer slot, a rehearsal or a deep dive. Run every notebook once in the workspace the day before and keep the checkpoints pre-opened (see each `run-of-show.md`).

## Before you start (once per workspace)

1. **Capacity and workspace.** A trial capacity runs these notebooks and pipelines. The data agent in Part 4 needs a paid capacity (F2 or higher). Create the workspace `ws-fleet-dev`. Sizing, regions and tenant settings are in `etl\rebuild-guide.md` section 2.
2. **Runtime.** Keep the workspace default, Fabric Runtime 2.0 (Spark 4.1, Python 3.13). Runtime 1.3 (Spark 3.5, Python 3.11; long-term support until March 2027) is the fallback if a notebook fails. Nothing was run in Fabric itself: the ETL notebooks passed 39 of 39 checks on Spark 4.1.1 + Delta 4.2.0 and on Spark 3.5.6 + Delta 3.2.1 (on a laptop and in GitHub Actions), and the ML notebooks ran on the Python libraries of both runtimes. The exact steps are in `etl\rebuild-guide.md` section 3, and the Spark calls to watch in the first run are in `ml-mlops\VERIFY-BEFORE-FRIDAY.md`.
3. **Lakehouse.** Create the schema-enabled lakehouse `lh_fleet`.
4. **Raw data.** Put the generated files under `Files/raw` (`etl\rebuild-guide.md` section 4 has five ways to do it). After an upload, wait about two minutes before running `nb_00_setup`: the file listing can lag.
5. **Items.** Get the notebooks and pipelines into the workspace in one of two ways:
   - **Import** the `.ipynb` files (`etl\notebooks\`, `ml-mlops\notebooks\generated-ipynb\`) and build the pipelines from the guides, or
   - **Git integration.** Copy the item folders of `etl\fabric-git\` and `ml-mlops\fabric-git\` into one repository folder and sync the workspace. The `logicalId` values already match across the two kits, so `pl_fleet_daily` finds `nb_01` to `nb_03`.
6. **Default lakehouse.** Attach `lh_fleet` as the default lakehouse of every notebook, then restart the session. Imports and Git syncs do not carry the binding into a new workspace.
7. **Shared ML code.** Upload `ml-mlops\notebooks\` (`__init__.py`, `notebook_common.py`, `shared\*.py`) to `lh_fleet`, folder `Files/code/notebooks`. Every ML notebook imports from it.

## If the ETL half is missing

Break-glass: load the reference tables with `..\06-demo-foundry-data-agent\fabric-setup\nb_10_load_gold_break_glass.py`, skip `nb_04` and `nb_07` (the loader already writes `ml.asset_day_features` and `ml.drift_report`), then run `nb_05`, `nb_06`, `nb_08`. `pl_fleet_daily` cannot run without the real ETL tables. Details are in `ml-mlops\README.md`.

## Checks you can run without Fabric

Run these from the workshop folder (the one that contains `02-demo-data`).

| Check | Command | What it proves |
|---|---|---|
| Fabric Git folders | `python 04-demo-fabric-e2e\tools\check_fabric_git.py --list` | File structure, `.platform` files, pipeline-to-notebook references across both kits |
| ETL on local Spark | `etl\local-validation\run_local.py`, then `compare_ground_truth.py` | The notebooks produce the exact counts of the data contract (needs Java and PySpark; about 10 minutes) |
| ML on local Python | `ml-mlops\local-validation\run_local.py`, then `compare_ground_truth.py` | Features, training, scoring, drift and gate match the contract (metrics within 0.03) |
| Fake Fabric run | `ml-mlops\local-validation\fabric_sim.py` | The generated Fabric notebooks run end to end with stand-ins for `spark` and `notebookutils` |
| ETL to ML hand-off | `ml-mlops\local-validation\integration_etl_to_ml.py` | The ML notebooks accept the tables the ETL notebooks actually write |

The same checks run in GitHub Actions on Linux (`.github\workflows\ci-data-ml.yml`, whenever `02-demo-data`, this folder or `ci\requirements` change): the ETL on Spark 3.5 and 4.1, the ML kit on a Runtime 2.0-like and a Runtime 1.3 library set, and the ETL to ML hand-off on three combinations of the two. All seven jobs were green when this kit was prepared. None of this ran in a real Fabric tenant. `..\VERIFY-BEFORE-FRIDAY.md` lists what to confirm there.

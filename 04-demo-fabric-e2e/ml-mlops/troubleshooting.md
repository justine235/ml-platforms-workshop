# Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `PREDICT` or generated scoring code refuses the model | Model signature missing | Re-run `nb_05_train_mlflow`; it logs the model with `infer_signature(...)` and an input example. |
| Registered model loads but scoring fails in Spark path | `synapse.ml.predict` unavailable in the current runtime/session | Use the pandas scoring path in `nb_06_register_score` (the path the notebook runs and the one validated locally; the `MLFlowTransformer` Spark path never ran outside a Fabric tenant). Check the runtime with `print(spark.version)` (`4.1.x` on the default Runtime 2.0, `3.5.x` on the Runtime 1.3 fallback; see "Runtime" below the table). |
| Experiment exists but the notebook cannot find it | Tracking URI or registry URI not set for the context | Verify `ensure_mlflow_experiment(...)` runs and the workspace-scoped Fabric MLflow configuration is active. |
| Wrong model version is scored | `ml.model_pointer` points to an older champion | Preview `ml.model_pointer` and either update it through `nb_08_promotion_gate` or pass `model_version` explicitly. |
| `nb_05_train_mlflow` stops at the end of training with a "table or view not found" error for `ml.model_pointer` (⚠ UNVERIFIED: not seen in Fabric yet) | A fresh workspace has no `ml.model_pointer`. `read_model_pointer` (`notebook_common.py:450-458`) treats a missing table as "no pointer yet": it returns an empty pointer when the exception class is named `AnalysisException` or the message contains `TABLE_OR_VIEW_NOT_FOUND`, `cannot be found` or `does not exist`, and re-raises everything else. That rule was tested only against a fake exception, so an error here means the real Fabric exception does not match it | Create the empty table once in a scratch notebook cell, then re-run `nb_05`: `spark.sql("CREATE TABLE IF NOT EXISTS ml.model_pointer (model_name STRING, champion_version STRING, updated_at_utc STRING, updated_by STRING, note STRING) USING DELTA")` (⚠ UNVERIFIED in Fabric). Note the exact exception class and message so `_is_missing_table_error` (`notebook_common.py:445-447`) can be adjusted. Details: `VERIFY-BEFORE-FRIDAY.md`, "Spark calls to watch in the first Fabric run". |
| Notebook cannot read/write the expected tables | Default lakehouse is not attached | Reattach `lh_fleet` as the default lakehouse in every notebook. |
| SQL endpoint table preview lags behind Spark write | Fabric metadata sync lag | Wait, refresh, or stay in Spark/Lakehouse table preview for the live demo. |
| Training behaves differently from the contract | Runtime package versions differ (the workspace runs the default Runtime 2.0; Runtime 1.3 is the fallback) | Check the workspace runtime against the "Runtime" paragraph below (`print(spark.version)` shows `4.1.x` on Runtime 2.0 and `3.5.x` on Runtime 1.3). Keep to the contract story: HGB metrics are approximate within ±0.03 (a local run gave the same HGB numbers on the Runtime 1.3 and the Runtime-2.0-like package sets; only logistic regression moved, by about 0.001). |
| Local validation or notebook import shows missing MLflow pieces | Different MLflow version or partial package install | Use the prescribed environment for validation; in Fabric, avoid ad hoc runtime package changes right before the demo. |
| Drift notebook writes nothing | `silver.telemetry_drift` missing | The ETL half's pipeline now produces `bronze.telematics_events_drift` and `silver.telemetry_drift` directly (re-run the ETL pipeline, not a manual rebuild); if ETL tables are unavailable, use the break-glass path and skip `nb_07` entirely (see README.md Prerequisites). |
| Pipeline notebook activity times out | Session cold start or capacity pressure | Increase timeout in the activity policy, warm the notebooks before the session, and keep one retry enabled. |
| Promotion gate compares the same version twice | Champion and challenger resolved to the same latest version | Supply explicit `champion_version` and `challenger_version`, or make sure more than one model version exists. |
| Permission error in pipeline alert activity | Office 365 connection missing or not shared | Rebind the `externalReferences.connection` value to a valid connection and test it from the pipeline UI. |
| Presenter cannot open Experiment or ML model items | Workspace role too low | Use Contributor or higher in the workspace. |
| Notebook session stalls or is evicted | Capacity pressure or long warm-up | Keep pre-run outputs open and avoid rerunning every notebook live if the room only needs the result table or UI. |
| `IfDriftAlert` branch never fires even on major drift | Expression uses `contains(string(activity(...).output), ...)`, which can never match because `string(...)` JSON-escapes the quotes nb_07 writes | Use the exit-value expression `@equals(json(activity('RunDriftMonitor').output.result.exitValue).status, 'alert')`; already fixed in the shipped `pipeline-content.json`. |
| `nb_07` prints `thresholds source: default` instead of `variable library` | `fleet_mlops` Variable Library not deployed/attached, or `driftModerateThreshold`/`driftMajorThreshold` names or value set are wrong | Check the library name and exact (case-sensitive) variable names, and that the right DEV/TEST/PROD value set is active; `get_env_setting(...)` silently falls back to the hardcoded default on any lookup failure. |
| Expecting the daily pipeline to auto-promote a challenger | `RunPromotionGate` passes no parameters, so `nb_08` always runs with `apply_pointer_update = False` -- this is by design, not a bug | Re-run `nb_08_promotion_gate` manually with `apply_pointer_update = True` to apply a promotion, or add an explicit `typeProperties.parameters` value to the activity for an auto-promote variant (documented as an optional exercise, not shipped). |

## Runtime

Keep the workspace default (Runtime 2.0: Spark 4.1, Python 3.13). Runtime 1.3 (Spark 3.5, Python 3.11; long-term support until March 2027) is the fallback. Nothing was run in Fabric itself. The ML notebooks ran end to end on the Python libraries of both runtimes [a Runtime-2.0-like set (pandas 2.2.3, numpy 2.5.4, scikit-learn 1.6.1, pyarrow 19.0.1, mlflow 2.22.0) and the Runtime 1.3 set (pandas 2.1.4, numpy 1.26.4, scikit-learn 1.2.2, pyarrow 14.0.2, mlflow-skinny 2.12.2)] and reproduced the contract on both: counts exact, metrics within the +/-0.03 tolerance. Those were local Python runs with a simulated Fabric and the ETL tables read through pyarrow, so the Spark calls of the ML notebooks (and Spark 4's ANSI default) were not exercised; they are listed in `VERIFY-BEFORE-FRIDAY.md`, "Spark calls to watch in the first Fabric run". The ETL kit passes 39 of 39 checks on local Spark 4.1.1 + Delta 4.2.0 and on Spark 3.5.6 + Delta 3.2.1 (Python 3.13.15, Java 17), also not in Fabric. Check the runtime with `print(spark.version)` (4.1.x on Runtime 2.0, 3.5.x on Runtime 1.3; see the ETL guide, `..\etl\rebuild-guide.md` section 3).
